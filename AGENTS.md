# Agent operating contract — Tessera

## Purpose and authority

Build Tessera from the supplied specifications and work packets. The user delegated ambitious autonomous implementation, not repeated planning sessions or a claim that vendor setup prevents all work. This seed is the plan. Read it and implement; a changed design needs a short recorded decision and tests, not wholesale reinvention.

Authority order: explicit latest founder instruction → shared founding decisions → shared integration contract/economic vectors → normative repo specs → task packet → implementation preference. Published legal/provider facts are not overridden by a convenient earlier assistant assertion. Proposed commercial defaults remain approval gates, not silently binding terms.

## Session workflow

Inspect actual repo state/status before assuming files exist or are complete. Select a coherent ready packet; read its inputs and dependencies. Make real code/tests; run them; inspect rendered UI where applicable; keep a work log with exact commands and outcomes. Commit or otherwise preserve all current code/artifacts before ending. Do not end with only a future plan when implementation was assigned.

When a task is too large for one session, finish useful vertical slices and save them, clearly marking incomplete acceptance conditions. Never erase existing working code to restart a preferred framework without evidence. Do not use placeholder screenshots, fake payments, fake chain IDs, untested “success” stubs or invented measurements as completion evidence.

## Parallel work

Use dedicated branches/worktrees. Own a packet's paths; coordinate shared schemas, lockfiles, migrations and APIs before editing. `Morpheus` is an independent repo integrated through versioned artifacts and identical contract snapshots. Do not copy application-specific concepts into Tessera core or reimplement economic logic inside Morpheus.

Shared files are read-only by default. Proposed contract changes require a version bump/decision, coordinated edits in both repos, regenerated fixtures and compatibility tests. Identical shared snapshots are checked by SHA-256; a drift must be resolved before integration release.

## Safety and spending

Local/test resources may be created within authorized tools. No purchases, real money transfers, mainnet deployment/funding, removal of upgrade authority, paid plan activation, irreversible license publication or binding account consent without explicit approval. Never invent personal/company/banking information, bypass CAPTCHA/MFA/KYC, or leak secrets into git/logs/screenshots/chat.

Public upload, signing, generation and payments have server-enforced caps/flags. Provider alerts are not hard spending controls. No production custody based only on a homemade encrypted test-key table. No legal ownership guarantees or “adapt anything and wait for complaints” behavior.

## Tools and verification

Use current official docs for changing APIs/prices. Prefer provider CLI/API when safe; use semantic browser automation for dashboard-only settings and inspect the actual result. Keep authenticated browser state out of source. Ask for the smallest unavoidable founder action once, record it, and continue independent work.

Windows note: development happens under Git Bash. `2>nul` creates a real file literally named `nul` that Git cannot add; use `2>/dev/null`. Solana/Anchor CLIs are absent; program build/test needs WSL2 or a cloud dev environment — record the gate and keep non-chain work unblocked.

For UI, create coherent designs, implement semantic controls and run browser visual/functional tests. A successful typecheck is not visual QA; a pretty page is not a working player. For money/chain, run deterministic/adversarial tests and preserve verified network/mode distinctions. A self-review is not an external audit.

## Completion report

List implemented outputs, tests with exact pass/fail evidence, screenshots/reports when relevant, any genuine external gates and the next ready packet. Update `status/WORK_LOG.md`, `status/SETUP_STATUS.md` and `BACKLOG.md`. “Done” requires packet acceptance, not merely code written or a task checkbox changed.
